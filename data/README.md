# Data

Nothing in `data/raw/` or `data/processed/` is committed to Git: of `raw/`
only the empty folders (`.gitkeep`) and `own_photos/dataset-metadata.json`.
Versioned are `data/splits/`, `data/labels/` and `data/reference/`.

## Folder layout

```
data/
├── raw/
│   ├── own_photos/     our own photos of the capture sheet (Kaggle, section 2)
│   ├── own_single_photos/  our photos of single bricks, not on the sheet (2a)
│   ├── internet/       photos and renders from TU Gdańsk: training data (2b)
│   ├── own_renders/    our renders from LDraw: training data (2d)
│   └── rebrickable/    Rebrickable CSV downloads
├── processed/          anything generated by our code (crops, resized images)
├── splits/             versioned: which photo is in which split
├── labels/             versioned: labels corrected by hand (sheets/: YOLO)
└── reference/          versioned: small hand-made tables (measured colours)
```

Rule: `raw/` is never edited by hand or by code. Everything derived goes
into `processed/` and must be reproducible from `raw/` with a script.

## 1. Kaggle renders (no longer used)

The first models were trained on the Kaggle set
[Images of LEGO Bricks](https://www.kaggle.com/datasets/joosthazelzet/lego-brick-images)
(J. Hazelzet, 40,000 renders of 50 parts). The code for it, its split
`data/splits/renders.csv` and the old configs are in the Git tag `v1-legacy`.
The folder `data/raw/renders/` can be deleted.

## 2. Our photos (evaluation)

One folder per part, e.g. `3001 brick 2x4/IMG_3415.jpg` (details in 2c).
Shared as the **private Kaggle dataset `gonsterenjoyer/lego-sheet-photos`**:
only team members added as collaborators can see it. Everyone needs the same
photos, because `data/splits/sheets.csv` and `data/labels/sheets/` refer to
them by name.

**Download** (once, and again after every new version):

```
kaggle datasets download -d gonsterenjoyer/lego-sheet-photos -p data/raw/own_photos --unzip
```

**Add photos:** put them into the right part folder (new part: new folder,
name like `3009 brick 1x6`, the code refuses other names), then upload a new
version. Run it inside the folder: with `-p data/raw/own_photos` the Kaggle
CLI fails on Windows (it builds a temp file name from the path).

```
cd data/raw/own_photos
kaggle datasets version -p . --dir-mode zip -m "s03: touching bricks"
```

Never rename or delete existing photos. `--dir-mode zip` is needed, without
it the Kaggle CLI skips all subfolders. `data/raw/own_photos/dataset-metadata.json`
(title, id, licence) is versioned in Git, so everyone in the team can upload
a version.

**Created once** (by the owner of the dataset):

1. `kaggle datasets init -p data/raw/own_photos`, then set `title` and
   `id` (`gonsterenjoyer/lego-sheet-photos`, no underscores) in
   `dataset-metadata.json`
2. in `data/raw/own_photos`: `kaggle datasets create -p . --dir-mode zip`
   (private by default)
3. on kaggle.com: dataset → Settings → Sharing → add the team's Kaggle
   usernames

## 2a. Older crops and single-brick photos (not used)

`data/raw/own_crops/`: crops of the sheet photos, cut on 2026-11-16 with the
first colour-threshold finder and checked by hand. No longer used: since
2026-11-21 `scripts/eval_own.py` evaluates the whole pipeline on the test
sheet photos instead. The older results on these crops can be reproduced with
the Git tag `v1-legacy`; the folder is no longer in the repo.

`data/raw/own_single_photos/<part folder>/`: photos of a single brick taken
without the capture sheet (so far 14 of 4073). Not used by any script yet;
they are kept apart so the internet loader only sees internet photos.

## 2b. Internet photos and renders (training data)

Source: T. M. Boiński, *LEGO bricks for training classification network*,
version 1.1 (2023-09-14), Gdańsk University of Technology, on
[MOST Wiedzy](https://mostwiedzy.pl/en/open-research-data/lego-bricks-for-training-classification-network,202309140842198941751-0)
(DOI [10.34808/wvms-q810](https://doi.org/10.34808/wvms-q810)). Licence:
version 1.0 of the set is CC BY; check the page for 1.1 and cite the set in
the report. Paper: Boiński, *Photos and rendered images of LEGO bricks*,
Scientific Data 10, 811 (2023).

The download (`05 - dataset.zip`, 6.0 GB) holds 447 parts: `photos/` (10 %
of the images) and `renders/` (90 %), each with one folder per part number,
single bricks on a white background. We use 18 of them, the parts of our own
photos except 4073 (not in the set). Copy their folders into
`data/raw/internet/photos/` and `data/raw/internet/renders/` and rename them
like our photo folders (`3001` → `3001 brick 2x4`; the set's `3062` is the
hollow-stud brick, our `3062b round brick 1x1`). The folder names are the
same as in `data/raw/own_photos/` (without `MIXED …` and 4073).

- `photos/<part folder>/`: 3,683 real photos of 18 parts, one brick per
  image, tightly cropped.
- `renders/<part folder>/`: ~43,000 coloured renders of 17 of these parts (no
  3062b), tightly cropped. Some folders also hold mould variants under their
  own number (3065 and 93792 in `3004 brick 1x2`, 30071 in `3005 brick 1x1`,
  ...): they count as the folder's part (code: `legorec.data.renders`).
- The label is the folder name. A file name like
  `c1_5_pcsp_original_3001_1609710513579.jpg` means camera 1 of capture
  `5_pcsp_original_3001_1609710513579`: all cameras of a capture show the
  same brick at the same moment.

Code: `legorec.data.internet`. The split file `data/splits/internet.csv` is
in Git; a missing capture is an error, so copy the folders completely.

## 2c. Sheet photos and YOLO labels (finding bricks)

What `data/raw/own_photos/` looks like at the moment (2026-11-20): one folder per
part with photos of the capture sheet (template v2), e.g.
`3001 brick 2x4/IMG_3415.jpg`, plus `MIXED 3009+3710+3023/` with several
parts per photo, and two tables:

- `labels_by_part.csv`: session and background of every photo
- `labels_mixed.csv`: true count per part and colour on the mixed photos

In both, the column `original` is the path relative to `own_photos/`
(`filename` points to a sorted copy that no longer exists).

YOLO-seg finds the bricks (one class "brick", see
`legorec.segment.labels`):

1. `python scripts/export_yolo.py`: warps every photo and writes a YOLO data
   set to `processed/yolo_bricks/`. The outlines are the corrected labels
   (step 3) or, where there are none, drafts of the current YOLO model.
   `review.csv` lists the photos to check first: every uncorrected val / test
   photo, because a new YOLO model is measured on those (against a draft of
   the old model, its mAP says little), then photos with suspicious outlines.
2. `python scripts/show_labels.py`: draws the labels onto the photos.
3. Wrong outlines: `python scripts/cvat_labels.py pack`, correct them in
   CVAT, `python scripts/cvat_labels.py unpack <export.zip>`. The corrected
   labels go to `data/labels/sheets/<photo>.txt` (**commit them**);
   `export_yolo.py` uses them instead of the drafts.
4. `yolo segment train data=data/processed/yolo_bricks/data.yaml
   model=yolo26n-seg.yaml imgsz=1024` (needs `pip install -e .[detect]`).
5. Copy `runs/segment/train/weights/best.pt` to `models/bricks_yolo.pt`.
   Then `python scripts/find_bricks.py <photo.jpg>` finds the bricks on a
   sheet photo and names their parts (`legorec.segment.bricks_on_sheet` in
   code).

## 2d. Our renders (training data)

`data/raw/own_renders/<part folder>/`: renders made by us with Blender and
the LDraw part library (`scripts/render_ldraw.py`, see its docstring), for
parts the internet set lacks or has few of: 3005, 3062b, 4073, 2,000 each so
far, plus `renders_manifest.csv`. Same file names as the internet renders
(`3005_Aqua_0_3000100000.jpeg`); the part number in the name must match the
folder. New renders are added to `data/splits/own_renders.csv` at the next
training start.

Not shared yet: ask David for the folder, or render them yourself (a few
hours on a GPU; the poses differ, so the split file gets new entries).

## Splits

Every split file maps a **group** to `train`, `val` or `test`. A group is a
set of images that must share a split, otherwise near-copies of training
images end up in the test set (code: `legorec.data.splits`). Never
regenerate a split file: results are only comparable on the same split.

`data/splits/internet.csv` assigns every **capture** of the internet photos
to `train`, `val` or `test` (70 / 15 / 15 %, stratified per part, all 18
parts). All cameras of one capture share a split. Never regenerate it either.

`data/splits/internet_renders.csv` and `data/splits/own_renders.csv` assign
every render **pose** (part + id in the file name; all colours of a pose) to
`train`, `val` or `test` (80 / 10 / 10 %). New renders in `own_renders/` are added to the file when
training starts (by a hash of their name); renders already in it never move.
Commit the file afterwards.

`data/splits/sheets.csv` assigns every **sheet photo** to `train`, `val` or
`test` (70 / 15 / 15 %, stratified per part folder). It is split by photo,
not by session: most parts were photographed in only one session, and for
finding bricks (one class) the part does not matter. New photos are added to
it like new renders (this changes with
[#61](https://github.com/BluePineappleCake/lego-recognition-fhdo/issues/61):
update this sentence then). Never regenerate it.
**Careful with the shape classifier**: a split by photo lets the model learn
the session (background, light) instead of the part. `own_photo_parts` in a
training config does exactly that for parts without internet data (4073):
on those parts, the numbers of `eval_own.py` are too optimistic.

No frozen test set yet: a new photo session, split by session, will become
`data/splits/test.csv`. Never train or tune on it; changes only after a team
decision in `#decisions`.

## Paths in code

Code reads the data location from the environment variable
`LEGOREC_DATA`, defaulting to `data/` (see `src/legorec/paths.py`).
Caches go to `LEGOREC_PROCESSED`, defaulting to `$LEGOREC_DATA/processed`.
On Kaggle the input folder is read-only, so set both:

```python
import os

os.environ["LEGOREC_DATA"] = "/kaggle/input/<our dataset>"  # contains raw/
os.environ["LEGOREC_PROCESSED"] = "/kaggle/working/processed"
```
