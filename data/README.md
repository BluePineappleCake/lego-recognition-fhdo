# Data

Nothing in `data/raw/` or `data/processed/` is committed to Git.
Only `data/splits/`, `data/labels/` and `data/reference/` are versioned.

## Folder layout

```
data/
├── raw/
│   ├── renders/        Kaggle render dataset (unzipped, unchanged)
│   ├── own_photos/     our own photos of the capture sheet
│   ├── labels/         CVAT exports for our photos
│   └── rebrickable/    Rebrickable CSV downloads
├── processed/          anything generated by our code (crops, resized images)
├── splits/             versioned: which photo is in which split
├── labels/             versioned: labels corrected by hand (sheets/: YOLO)
└── reference/          versioned: small hand-made tables (measured colours)
```

Rule: `raw/` is never edited by hand or by code. Everything derived goes
into `processed/` and must be reproducible from `raw/` with a script.

## 1. Renders (training data)

Source: [Images of LEGO Bricks](https://www.kaggle.com/datasets/joosthazelzet/lego-brick-images)
by J. Hazelzet (40,000 images, 50 part types).

**Option A: Kaggle CLI**

1. Create an API token on kaggle.com → Settings → API → *Create New Token*
2. Put the downloaded `kaggle.json` into `~/.kaggle/`
   (Windows: `C:\Users\<you>\.kaggle\`)
3. Run from the repo root:

```bash
pip install kaggle
kaggle datasets download -d joosthazelzet/lego-brick-images -p data/raw/renders --unzip
```

**Option B: manual**
Download the ZIP from the Kaggle page and unzip it into `data/raw/renders/`.

**On Kaggle Notebooks** nothing needs downloading: add the dataset via
*Add Input*, it appears under `/kaggle/input/`.

## 2. Our photos (fine-tuning and test)

Stored in our private Kaggle dataset `<name-tbd>`. Download the same way
into `data/raw/own_photos/`.

Each capture session gets its own folder:

```
own_photos/
├── 2026-11-04_s01/
│   ├── IMG_0001.jpg
│   └── ...
└── photos.csv
```

`photos.csv` has one row per photo:

| column | example | meaning |
|---|---|---|
| `file` | `2026-11-04_s01/IMG_0001.jpg` | path relative to `own_photos/` |
| `session` | `s01` | capture session |
| `camera` | `pixel7` | device used |
| `light` | `2xLED` | lighting setup |
| `n_bricks` | `6` | number of bricks in the photo |
| `layout` | `separated` | `separated` or `pile` |

Adding new photos: create a new session folder, add rows to `photos.csv`,
upload a new version of the Kaggle dataset. Never rename or delete
existing photos, the splits refer to them by path.

## 2b. Internet photos (extra real data)

Source: tbd (name, link and licence also go into `Quellen.txt`).
Unzip into `data/raw/internet/` so that `data/raw/internet/photos/` exists,
or pass the folder with `--data`.

- `photos/<part folder>/`: 3,683 real photos of 18 parts, one brick per
  image, tightly cropped. 13 parts are among our 50 render classes; the other
  5 (2654, 3009, 3666, 3710, 6215) are not.
- `renders/`: ~44,000 coloured renders of the same 18 parts. Not used yet.
- The label is the folder name. A file name like
  `c1_5_pcsp_original_3001_1609710513579.jpg` means camera 1 of capture
  `5_pcsp_original_3001_1609710513579`: all cameras of a capture show the
  same brick at the same moment.
- Tightly cropped: the brick size in pixels says nothing about the real
  size, so do not use `size_feature` with these photos.

Code: `legorec.data.internet`. Overview and split check:
`python scripts/internet_split.py --data <folder>`.

## 2c. Sheet photos and YOLO labels (finding bricks)

What `data/raw/own_photos/` looks like at the moment (2026-11-20): one folder per
part with photos of the capture sheet (template v2), e.g.
`3001 brick 2x4/IMG_3415.jpg`, plus `MIXED 3009+3710+3023/` with several
parts per photo. `lego-real-photos/` is a sorted copy of the same photos
with `labels_by_part.csv` (session, background) and `labels_mixed.csv`
(true count per part on the mixed photos); the code skips the copies.

YOLO-seg finds the bricks (one class "brick", see
`legorec.segment.yolo`):

1. `python scripts/export_yolo.py`: warps every photo, draws the brick
   outlines with `find_bricks` and writes a YOLO data set to
   `processed/yolo_bricks/`, plus `review.csv` (photos to check first).
2. `python scripts/show_labels.py`: draws the labels onto the photos.
3. Wrong outlines: `python scripts/cvat_labels.py pack`, correct them in
   CVAT, `python scripts/cvat_labels.py unpack <export.zip>`. The corrected
   labels go to `data/labels/sheets/<photo>.txt` (**commit them**);
   `export_yolo.py` uses them instead of the automatic ones.
4. `yolo segment train data=data/processed/yolo_bricks/data.yaml
   model=yolo26n-seg.yaml imgsz=1024` (needs `pip install -e .[detect]`).
5. Copy `runs/segment/train/weights/best.pt` to `models/bricks_yolo.pt`.
   Then `python scripts/find_bricks.py <photo.jpg>` finds the bricks on a
   sheet photo and names their parts (`legorec.segment.bricks_on_sheet` in
   code).

## Splits

`data/splits/renders.csv` assigns every render **pose** to `train`, `val` or
`test` (80 / 10 / 10 %, stratified per part). Each pose exists twice (cameras
L and R); both views always share a split, otherwise near-copies of training
images end up in the test set. Never regenerate this file: all render results
are only comparable on the same split.

`data/splits/internet.csv` assigns every **capture** of the internet photos
to `train`, `val` or `test` (70 / 15 / 15 %, stratified per part, all 18
parts). All cameras of one capture share a split. Never regenerate it either.

`data/splits/sheets.csv` assigns every **sheet photo** to `train`, `val` or
`test` (70 / 15 / 15 %, stratified per part folder). It is split by photo,
not by session: most parts were photographed in only one session, and for
finding bricks (one class) the part does not matter. Never regenerate it.
**Do not use it for the shape classifier**: there a split by photo would
let the model learn the session instead of the part (see below).

`data/splits/finetune.csv` and `data/splits/test.csv` list photo paths.

- Splits are made **by session**, never by single photo. Photos from the
  same session (same bricks, same light) must not end up in both splits.
- `test.csv` is frozen once created. Never train, fine-tune or tune
  thresholds on it. Changes only after a team decision in `#decisions`.

## Paths in code

Code reads the data location from the environment variable
`LEGOREC_DATA`, defaulting to `data/` (see `src/legorec/paths.py`).
Caches go to `LEGOREC_PROCESSED`, defaulting to `$LEGOREC_DATA/processed`.
On Kaggle the input folder is read-only, so set both:

```python
import os

os.environ["LEGOREC_DATA"] = "/kaggle/input"
os.environ["LEGOREC_PROCESSED"] = "/kaggle/working/processed"
```

The render folder on Kaggle does not follow our layout; pass it directly:
`--data /kaggle/input/datasets/joosthazelzet/lego-brick-images/dataset`.
